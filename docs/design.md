# Design: packlight, keep your coding agent carrying only what you use

Generated by /office-hours on 2026-10-07 (inline, during /plan-ceo-review)
Branch: docs/public-refusals-draft (essent-hq); target repo is new
Repo: cooperism-lab/packlight (to be created)
Status: APPROVED (2026-10-07, after three adversarial review rounds, 8/10)
Mode: Builder

## Problem Statement

Solo developers using AI coding agents accumulate skills, agents, hooks, plugins and MCP connectors and never see what each one costs or whether it is used. Measured on the builder's own machine (Claude Code, 102 sessions, 20 Aug to 7 Oct 2026): 282 installed items, 238 not observed in any session; one plugin's session-start hook injected about 7,400 characters into every session (1.5M total); a project hook fired 5,491 times; a settings line had silently routed every session to a smaller model.

The cost is not what the spec first assumed. Claude Code 2.1.129 and later caps the skill listing at about 1% of the context window (`skillListingBudgetFraction`, verified present in the installed 2.1.289 binary) and drops the least-used skills' descriptions entirely when the budget is exceeded. So unused skills do not cost tokens every session; they push the skills you want out of the listing, and those stop firing. Hooks are not capped. MCP tools are now loaded lazily.

## What Makes This Cool

- **Rescuing buried skills.** The report can name the skills that would become discoverable again if you archived the ones you never use. That is a headline nobody else has.
- **"Which one" cards.** For similar skills, a card that says "use A when…, use B when…, example invocation" instead of a merge recommendation. The builder's own words: "or maybe it is just similar how can help user know which one to use".
- **Reversible by design.** Archive writes a manifest; restore is exact; `restore --all` undoes everything packlight ever did. Delete is a separate, later, typed-confirmation step.

## Constraints

- Local only: no telemetry, no network calls from the CLI or the report. Ratings run inside the user's own agent (no API key).
- The report is one self-contained HTML file that works without the agent; ratings are an add-on from the skill.
- Nothing is removed without the user's confirmation, and never silently.
- Usage counts come from local session logs only, so the wording is "not observed in N sessions", never "unused": claude.ai and Cowork use is invisible to them.
- TypeScript, run with `npx packlight`; name free on npm and PyPI as of 2026-10-07.
- The scanner never executes hook commands or any scanned code; it reads files and session logs only. Hook sizes and firing counts come from the logs' recorded hook results, never from running them.
- Every archived item is hashed (SHA-256) when archived; restore verifies the archived copy against that hash before writing anything.

## Removal methods (the five, and what each covers)

| Method | Item kinds | Source | Manifest fields | Restore |
|---|---|---|---|---|
| `move` | personal skills, personal and project agents, mods | `~/.claude/skills/<name>`, `~/.claude/agents/*.md`, `.claude/agents/*.md`, mod folders | originalPath, isSymlink, symlinkTarget, sha256 of a tar of the folder | move back; refuse if originalPath is occupied |
| `hook-extract` | hooks declared in settings files | `~/.claude/settings.json`, `settings.local.json`, project `.claude/settings*.json` | settingsFile, jsonPointer, fragment, originalFileBytes (the whole file as it was), fileHashBefore, fileHashAfter | see conflict rule below |
| `mcp-extract` | MCP servers in JSON config | `~/.claude.json` `mcpServers`, project `.mcp.json` | same fields as hook-extract | same as hook-extract |
| `plugin-disable` | plugins, and every skill, agent, hook or server a plugin bundles (the Vercel session-start hook is one of these) | `enabledPlugins` in `~/.claude/settings.json` | plugin key, wasEnabled, plus the same settings-file fields as hook-extract (jsonPointer, originalFileBytes, fileHashBefore, fileHashAfter) | same as hook-extract: byte restore when untouched, else set the flag back by a parse-and-serialize edit; refuse if the plugin key is gone |

Codex's `config.toml` is TOML, so it has no JSON pointer and no format-preserving edit in v1: Codex MCP servers are report-only (listed with their cost, not archivable) until the v0.3 adapter adds a TOML-preserving edit or the same byte-restore path.
| `manual` | claude.ai skills and connectors, desktop extensions, Chrome extensions | web or app settings | where to click | not restorable by packlight; listed as "waiting for you" until a rescan confirms |

Editing inside a plugin's own files ("plugin surgery") is not in v1: a bundled item is archived by disabling its plugin, and the report says so on the card.

## Restore conflict rule

- `move`: verify the archived tar's hash; if `originalPath` now exists, refuse that item and say what is there.
- `hook-extract` and `mcp-extract`: if the settings file's current hash equals `fileHashAfter` (untouched since archive), write `originalFileBytes` back, so the file is byte-identical to before. If the file changed since, re-insert the fragment at `jsonPointer` with a parse-and-serialize edit (semantic restore) and report that formatting may differ; if the pointer no longer resolves, refuse that item.
- `restore --all`: restores every item it can, lists each refused item with its reason, and exits non-zero if any was refused. Nothing is overwritten to force a restore in v1.

## Premises (agreed 2026-10-07)

1. The pain is lost discoverability (least-used skills silently lose their descriptions) plus uncapped hook injection, not description tokens. Hero metrics: skills over budget, and characters hooks inject per session.
2. Reversible archive, never silent, is the right action primitive; delete is separate and later.
3. Local only; ratings via the user's own agent.
4. Distribution is npm plus a skill; Claude Code first, Codex second.

Where this design differs: hooks stay in the first release. Settings-file hooks are archived by `hook-extract`; a plugin's hook (the builder's largest finding, the Vercel session-start hook) is archived by `plugin-disable`, which turns the whole plugin off. Editing inside a plugin is what is deferred.

## How the pieces connect

- **Picks hand-off.** The report is static and makes no network requests. **Save my picks** downloads `packlight-picks-<scanId>.json` (`{ scanId, createdAt, picks: [{ id, action: "archive" | "keep", note }] }`) to the browser's download folder. `packlight apply [picks.json]` consumes it, defaulting to the newest picks file in `~/Downloads`; it refuses a file whose `scanId` is not the newest scan for that agent, and skips any item whose description hash changed since the scan. The report and the CLI's closing line both print the exact command.
- **Ratings.** The packlight skill reads `~/.packlight/scans/<scanId>/inventory.json` and writes `ratings.json` beside it: one entry per item id with `what`, `when`, `how`, `usefulness` 1-5, `efficiency` 1-5, `verdict` (keep / review / archive), `note`, `descHash`. It also writes `groups.json` for the which-one cards. `packlight report` regenerates the HTML with both files merged in; without them the rating fields render as "Not rated yet, install the packlight skill". **Incremental** means the skill rates only items whose `descHash` is new or changed since the last `ratings.json`. **Picks suggestion** means: whenever the skill runs, it checks for a picks file newer than the last apply and proposes `packlight apply`; it never applies on its own, and it never adds items to the picks.
- **Budget finding.** First choice: parse Claude Code's startup budget warning from the session logs, which names the dropped skills. Fallback: recompute from `skillListingBudgetFraction` (default 0.01), `skillListingMaxDescChars` (default 1536), the model's context window (taken from the session's model id, with a table of known windows and 200k as the default) and the ordering rule "most-invoked first, ties by name"; a recomputed list is labelled an estimate. Criterion 5 below holds only where the warning was found in the logs.
- **Codex adapter (v0.3, after Issue 1 has verified the sources).** Reads `~/.codex/sessions/YYYY/MM/DD/rollout-*.jsonl` (usage: SKILL.md reads and tool calls recorded in rollouts), `~/.codex/config.toml` (`[mcp_servers.*]`), `~/.codex/skills/`, `~/.codex/plugins/` and `AGENTS.md` (always-loaded cost). Codex has no hook system and no listing budget, so hook and budget findings are Claude Code only; the Codex report shows inventory, usage and description size.

## Approaches Considered

### Approach A: Minimal loop (ruled out by the builder on 2026-10-07)
Scan Claude Code, usage with the "not observed" wording, budget and hook findings, static report with Save my picks, archive and restore for skills and hooks. Effort S-M, risk low. Rejected because the builder wants the ratings and which-one cards in the first public release (v0.2) rather than a later one; the Codex adapter follows in v0.3.

### Approach B: Full spec, all seven issues (chosen)
The minimal loop plus overlap groups, settings doctor, the packlight skill (profile, incremental ratings, which-one cards, picks suggestion), the Codex adapter, packaging and CI. Effort XL, risk medium. Reuses the Python prototype's parsing and the Toolkit Ledger's report layout.

## Recommended Approach

Approach B, with two corrections carried from this session into the spec before any issue is filed:
- Replace "tokens loaded every session" with two hero metrics: **skills over the listing budget** (and which ones would come back under it) and **characters hooks inject per session start and per tool call**. Keep a labelled estimate of description size for Codex, which has no such budget.
- Use "not observed in N sessions" wording everywhere, with the scan's date range and parsing gaps shown.

The prototype that stands in for a wireframe is live: the Toolkit Ledger (claude.ai artifact 7Du2T8xgbpvHe4hWEr5ys2, version 5), a monitoring-dashboard layout with an Overview hero, KPI cards, and table views per kind. Its hero number is the one this design corrects.

## Open Questions

1. Is Claude Code's startup budget warning written to the session logs? If it is, the budget finding is exact; if not, the recomputation fallback above ships and is labelled an estimate. Issue 1 answers this on the builder's own logs first.
2. Agents: are their descriptions budgeted too? The one source consulted says no; verify against the binary before treating agents as uncapped.
3. claude.ai connector ids appear in desktop-app logs as opaque uuids. Is there a local file mapping them to display names?
4. Licence: MIT unless the builder prefers Apache-2.0.

## Success Criteria

- On a fixture home folder, scan counts match the hand-counted expected file exactly, by kind and source; hook firings and injected characters are attributed by the `command` field.
- Archive then restore leaves the home folder byte-identical for `move`, `plugin-disable`, `hook-extract` and `mcp-extract` when nothing touched the files in between (checked by a diff of the fixture home folder); when a settings file was edited in between, the restored JSON is semantically equal and the report says formatting may differ. `manual` items are checked by the next scan.
- `npx packlight` reaches an opened report in under 120 s on a cold cache, under 30 s on the builder's 1.3 GB of logs.
- The report makes zero network requests and renders at 400 px wide.
- Where the startup budget warning is present in the logs, the budget finding names the skills currently dropped, and a re-scan after archiving shows the ones that came back; where it is absent, the finding shows the recomputed estimate with that label.

## Distribution Plan

- npm package `packlight`, run with `npx packlight`; `packlight install-skill` copies the skill into `~/.claude/skills` or `~/.codex/skills`.
- GitHub Actions: test on macOS and Linux on every push; publish to npm on a tagged release.
- README opens with the builder's own before/after numbers.
